# ひとひ 再構築の計画（v2）

目的：`docs/PRODUCT.md` の仕様を、**バグが構造的に起きにくい土台**の上に作り直す。
v1 の継ぎはぎは引き継がない。ただし、問題が出ていない部品（暦の計算・保存・控え・読む画面の描画）はテスト付きで移植してよい。

この計画は出発点。より良い方法があれば、理由を `docs/` に書いた上で変えてよい。ただし `CLAUDE.md` の大原則は守る。

## 1. 土台の推奨

| 項目 | 推奨 | 理由 |
|---|---|---|
| 形 | PWA のまま（Safari →ホーム画面に追加） | ネイティブアプリには Mac と有料の開発者登録が要る |
| 言語 | TypeScript | 名前の変え忘れ・使われていない処理などを、公開前に機械が見つける |
| 組み立て | Vite（小さく速い）。組み立ては GitHub Actions に任せる | 手元の PC に何も入れなくても公開できる |
| テスト | ロジック：Vitest／画面の流れ：Playwright（**WebKit**） | Safari と同じエンジンで流れを確かめる |
| 公開 | GitHub Actions → GitHub Pages。本番 `/hitohi/`、試作 `/hitohi/beta/` | 本番の日記を壊さずに試せる |
| 依存 | 実行時の外部ライブラリは使わない（書体の Google Fonts のみ） | 300kbps・オフライン・長く保守できること |

試作版は保存場所を分ける（DB 名 `hitohi-beta` など）。同じ `teto59.github.io` の中は保存場所が共有されるため。

## 2. 画面の作り（v1 の失敗を踏まえて）

### 書く画面
- **本物の textarea をそのまま見せる。** 書体 Klee One 600、罫線は textarea 自身の背景に（文字と一緒にスクロールする）。
- 入力中のスクロールは textarea 自身に任せる（中身に合わせて高さを伸ばす作りは避ける）。カーソルを追いかける処理は書かない。
- 上部に固定の見出し帯：「‹ 暦」「日付」「綴じる」。スクロールしなくても、キーボードが出ていても押せること。
  - iOS はキーボードを出す時に画面全体をずらすことがある。見出し帯が画面外に押し出されないことを **実機で** 確かめる。
    対策が必要なら、visualViewport の高さに枠を合わせる処理を **一つだけ**、最小限に書く（スクロールのたびに動かす作りは禁止）。
- 字数はひかえめに表示。
- 自動保存・全部消した時の確認・保存失敗の知らせは v1 の考え方を引き継ぐ。

### 読む画面・暦・栞
- 読む画面：一文字ずつの揺らぎ＋鉛筆のかすれ（v1 の `renderHand` と CSS マスク）を移植。禁則も。
- 暦：v1 の見た目と計算を移植。月齢・二十四節気は **既知の日付でテスト** する
  （例：2026 年の新月 11/9 付近、満月 11/24 付近、立冬 11/7、小雪 11/22）。
- 栞：音の設定は無くす。控え（書き出し・読み込み）と、最後に書き出した日、朱の点。

### 引き継ぎ
- v1 で書かれた日記（IndexedDB `hitohi` / `entries`）は、v2 でそのまま読めること。**テストで保証する。**
- v1 の設定（`hitohi-settings` の `soundLevel` `lead` など）は無視してよい。`lastExport` は引き継ぐ。

## 3. 進め方（段階と合格条件）

各段階の終わりに、利用者へ平易な言葉で報告する。

1. **土台**：TypeScript・Vite・テスト・GitHub Actions（本番と試作の二つの公開先）。
   合格：空の画面が試作アドレスで開ける。テストが CI で動く。
2. **暦・読む・保存・控え**（v1 から移植）。
   合格：自動テスト（暦の計算、v1 データの読み込み、控えの往復、禁則）がすべて通る。
3. **書く画面**（作り直し）。
   合格：WebKit の自動テスト（書く→綴じる→朱印→読む、全部消して確認、保存失敗の知らせ）が通る。
4. **試作版を公開** → 利用者が `docs/CHECKLIST.md` で iPhone 実機確認。
   合格：チェックリストがすべて「はい」。だめな項目は直して、もう一度。
5. **本番へ切り替え**。切り替え前に、利用者に栞から控えを書き出してもらう。

## 4. 実装で決めたこと（2026-11-19、段階 1〜3）

計画から変えた点・付け足した点と、その理由。

### 公開の仕組み
- GitHub Pages の公開元を「main の直下」から「GitHub Actions」に変えた（`.github/workflows/deploy.yml`）。
  テストが一つでも通らなければ公開しない。
- 本番に何を出すかは `site.config.json` の `production` で決める。**合格が出るまで `"v1"`**（`v1/` フォルダをそのまま出す）。
  `v1/` は v1 の本体を 1 バイトも変えずに移したもの（テスト「いま本番に出ているのは v1 そのもの」で毎回確かめる）。
- 試作版は `dist/beta` を `/hitohi/beta/` に出す。保存場所は DB `hitohi-beta`、設定 `hitohi-beta-settings`、
  オフラインの控え `hitohi-beta-*`。アイコンには「試作」の帯（`brand/icons-beta/`、`scripts/make-beta-icons.mjs` で作る）、
  名前は「ひとひ（試作）」。栞のいちばん下に版の名前（例：`版 2.0.0（試作）　2026-11-19　abc1234`）を小さく出す
  （実機で、どの版を確かめているか分かるように）。

### 試作版への入口の手当て（`src/beta-shim.js` → `beta/app.js`）
- 本番 v1 の Service Worker は `/hitohi/` の下の画面を**すべて**引き受け、控えた v1 の画面を出す作りになっている。
  そのため、v1 を入れた Safari で `/hitohi/beta/` を開くと v1 の画面（の骨組み）が出てしまう。
- そこで出てくる v1 の画面は、同じ場所の `app.js`（＝ `/hitohi/beta/app.js`）を読みに来る。試作版ではそこに小さな手当てを置き、
  試作版の Service Worker（受け持ち `/hitohi/beta/`）を入れてから開き直す。より細かい場所の仕組みが優先されるので、以後は試作版が出る。
- 本番の中身も本番の日記も変えずに済む方法として選んだ。テスト「本番 v1 の仕組みが入っている Safari でも…」で確かめている。
- v2 の Service Worker は、本番でも `beta/` の通信には手を出さない（`CONFIG.skip`）。控えの名前も分け、自分の控え以外は消さない。

### 画面
- 書く画面：本物の textarea を全面に。罫線は textarea 自身の背景（`background-attachment: local`）。
  上の帯「‹ 暦／日付と字数／綴じる」は画面の枠の一部で、動かない。下の帯はない（キーボードと競わないため）。
- 読む画面も、書く画面と同じ形の上の帯「‹ 暦／日付・朱印と字数／なおす」にした（「なおす」→「綴じる」が同じ位置になる）。
- キーボード対策は `src/viewport.ts` の一つだけ：見えている範囲の**大きさ**が変わった時（キーボードの出入り）に、
  枠の高さをそれに合わせ、ページ全体がずれていたら戻す。スクロールには反応しない。
  キーボードが出た直後に一度だけ、カーソルが末尾なら末尾が見えるよう入力欄を送る（入力中は何もしない）。**実機で要確認。**
- v1 にあった「ブラウザの戻る（履歴）」は付けなかった（仕様にない。書いている途中に画面が切り替わる入口を増やさないため）。
- 書体の目録（Google Fonts の CSS）を `crossorigin` 付きで読むようにした。v1 は付けておらず、端末に控えられないため、
  圏外では手書きの書体が出ていなかった（v1 の不具合。v2 で直した）。

### テスト
- `npm run check`：型の確認 → ロジック（Vitest 47 件）→ 組み立て → 画面の流れ（Playwright・WebKit 29 件）。CI でも同じ。
- **本物の v1** で日記を書き（v1 の画面を操作）、配信を v2 の本番版に切り替えて、同じ端末で全部読めることを確かめる
  （`tests/e2e/v1-to-v2.spec.ts`。配信の切り替えは `scripts/serve.mjs` の Cookie で再現）。
- パソコンの WebKit では、iPhone のキーボード・変換・音声入力・ホーム画面アプリの挙動は再現できない。そこは実機で確かめる。

### 段階 4 の結果
- 2026-11-19、試作版（版の 7 桁 `aae353a`）で `docs/CHECKLIST.md` の 1〜19 がすべて合格。
  途中で見つかった 19（控えと一緒に短いテキストファイルができる）は直して再確認済み。

### 本番に出す仕組み（切り替えの時に決めた）
- 「本番 = main の最新」にすると、以後の変更が試作版の確認なしに本番へ出てしまう（大原則 3 に反する）。
  そこで本番は、試作版で合格した版を本番用に組み立てて `releases/<7桁>/` にコミットし、それを 1 バイトも変えずに出す。
  試作版は main の最新。本番を変えるのは `npm run release -- <7桁>` と `site.config.json` の変更だけ（手順は `CLAUDE.md`）。

### 段階 5（本番への切り替え）の手順
1. 利用者が本番アプリの栞から控えを書き出す（`docs/CHECKLIST.md` の 20）。→ 2026-11-19 済み。
2. `npm run release -- aae353a` で `releases/aae353a/` を作り、`site.config.json` の `production` をそこに向けて main に入れる
   （テストが通れば自動で公開される）。
3. 利用者に、通信のある所で本番アプリを一度開き、数秒待ってもらう。v1 の仕組みが新しい版を取り込み、v2 に開き直る。
   （取り込みの途中でアプリを閉じ、次に圏外で開くと、一度だけ画面が出ないことがある。その時は通信のある所で開き直す。）
4. `docs/CHECKLIST.md` の 21 を確かめてもらう。
5. `v1/` は残す（v1 で書いた日記を読めるかのテストに使い、万一の戻し先にもなる）。`site.config.json` と `releases/` は以後のリリースの仕組み。

## 5. 再構築でやらないこと

- 音（`sound/` は使わない。消してよい）。
- 書いている最中の一文字ずつの揺らぎ・かすれ・インクがにじむ演出（入力欄の偽装が必要になるため）。
- 仕様書にない機能の追加。
